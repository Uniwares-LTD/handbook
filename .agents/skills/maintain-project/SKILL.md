# Maintain Project

Read [bootstrap](../../../docs/bootstrap.md), [onboarding](../../../docs/onboarding.md)
and [project ownership](../../../docs/project-guidance.md) at the task revision.

Inputs: the authorized destination, existing instructions and accepted adaptations,
canonical project documents, stack evidence and integration metadata. Inspect before
writing; an existing checkout or project link does not establish adoption authority.

For authorized local initialization or maintenance:

1. Resolve project identity from canonical configuration and repository evidence.
2. Reconcile guidance and the compact project-owned source map; link existing sources.
3. Select relevant technology skills; preserve local constraints and explain conflicts.
4. Reconcile bootstrap files and native entrypoints following the README route.
   Use explicit sync; never overwrite customized wrappers or replace project AGENTS.md.
5. Run offline readiness/drift checks and the appropriate setup/check/doctor command.
   Keep baseline availability separate from advisory local readiness.
6. Report changes, provenance, checks, limitations and remaining human acceptance.

External project creation or enrollment proposals are optional when relevant to the
user's goal. They are not required for local setup and grant no external-write authority.
Do not create projects, credentials, issues or backlogs to demonstrate this workflow.
Derived-project creation remains offline and copies only permitted bootstrap material.

Completion: local guidance, source-map routing and selected entrypoints are reconciled,
checks are reported honestly, and unresolved conflicts/unknowns have clear next actions.
Use existing documentation/learning/issue skills for subsequent focused maintenance.

## Organization-owned work tracking

When tracking setup is authorized, follow [project operations](../../../docs/project.md).
Resolve the repository organization, inventory accessible projects and accepted queues,
and distinguish missing access from no projects. On first selection offer reuse, dedicated
repository project or organization-wide project, defaulting to organization-wide. Ask the
issue language (English by default, or Persian) and record it in the repository
preferences declared in handbook.json. Retain later recorded choices.
Keep identity/mappings and policy references in consumer-owned tracking metadata.
Preview exact project/field/view/link changes and conflicts before applying authorized
operations; verify readback and disclose manual steps, including the browser-only
workflow configuration. Tracking setup is complete only when its setup acceptance in
project operations is met; otherwise report it as partial. Preserve custom content, permissions,
existing items and legacy queues. No demonstration issues or implicit migration.
Before a local workflow override, assess promoting the improvement to shared guidance;
record a local rationale when specialization is necessary. Shared publication is separate.
